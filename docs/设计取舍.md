## 时间戳

**每条输出都带时刻。** 你要判断的从来不是「它 idle 多久了」，而是「它什么时候开始闲的」
和「它现在这个状态是什么时候进入的」——只有时长没法判断是刚做完还是卡了半天。

```bash
$ xteam status
xteam status  2026-10-01 16:24:31   workspace='apartment' (wD)
project=/Users/you/Server/apartment

role  状态      持续     起始于         最后活动        义务 / 在哪
pm    idle      18m20s   10-01 16:06:11  10-01 16:06:11  none
tl    working   0s       10-01 16:24:29  10-01 16:24:29  chase checkout
dev   idle      4m12s    10-01 16:20:19  10-01 16:20:19  consume checkout
```

`xteam say` 和 `xteam watch` 的输出也都带调用时刻。

### 三个角色共享一条时间线

```bash
xteam stamp dev "delivery 2 已提交，84/84"        # 记一行
xteam stamp pm "等你拍板结算口径" --waiting       # 声明在等你，不是卡死
```

时间戳由脚本生成，不手写——手写的可靠性等于「写的人对自己何时看过表」的记忆，实测漂过。
三个 pane 的时刻落在 `.xteam/watch/timeline.log` 同一条线上，可以直接排出
「谁在什么时候把活交给了谁」。

`--waiting` 有实际作用：巡检看到某角色声明在等人类，就**免打扰但不静默**（仍记
`SUPPRESSED` 事件）。否则「被免打扰」和「没人管」在日志里长得一样。

## 设计要点

### 状态是文件，不是看板

`.xteam/tasks/<slug>/` 下每个文件代表一级推进，谁写哪个文件是固定的。没有看板、没有卡、
没有分支、没有 35 个命令。

**「没有 worktree」这条在解锁重叠时改了口径。** 原来靠「交付到判定之间整棵树冻结」
换可归因，代价是 dev 交付后必须干等（本仓实测每片 3–12m）；现在换成
**按 `changed[]` 钉一个交付提交**（`xteam snap`），judge 在 `xteam review-tree`
临时钉出的快照树里做 —— 树继续往前跑，归因跟着提交走。快照树是**判据的载体**：
`--detach`、片闭合即清，不是开发分支，也不是「谁的 workspace」。

```
spec.md → request.md → delivered.json → ready.json → verdict.json → consumed.json → closed.md
  PM        TL           DEV            TL            PM             DEV            PM
```

完整协议见 [templates/PROTOCOL.md](../templates/PROTOCOL.md)（`up` 会拷进项目的 `.xteam/`）。

### 义务由协议算，不由时长猜

这是整套东西的核心。`xteam status` 给每个角色算一个 `owes`：

```
role  状态      义务        在哪
pm    working   gate        checkout
tl    idle      none        -
dev   idle      consume     checkout
```
判据是**「它有没有未消费的交付」**，不是「它 idle 了多久」：

- `idle` + `owes: none` → **真做完了**，合法终态，不报警
- `idle` + `owes: consume` → **卡住了**，该催
- `working` → 正常，不打扰
- `blocked` → 停在审批 UI，**不替它回答**，报给你

这一条把「防停摆」和「防误报」同时解决了。靠超时报警做不到：做得快的角色会被反复
骚扰，真卡死的角色和认真干活的角色在超时面前没有区别。

### 交接工件都带轮次

`delivered.json.round`（第几次交付）、`verdict.json.round`（第几次判定）、
`ready.json.delivery`（放行的是第几次交付）、`verdict.json.delivery`（判的是第几次交付）。

**为什么必须带**：工件一旦 FAIL 就一直躺在目录里，下一轮还会被看到。没有轮次就分不清
「上一轮的 ready」和「这轮该出的 ready」，FAIL 之后链路直接死锁——三个人都不欠活。
这个 bug 是写测试时真撞出来的，不是预防性设计。

### 角色边界（防止自审和越界）

| 角色 | 做 | 不做 |
|---|---|---|
| pm | 对接你、grill、出 spec、判 PASS/FAIL、巡检 | 不写产品代码，不替 TL 拆解 |
| tl | 拆解、细化、派活、持续 review、打回 | 不写代码，不判 PASS/FAIL，不做需求决策 |
| dev | 实现、自测、上报、修 | 不判 PASS/FAIL，不超出 request 范围，不急着往前做 |

PM 兼 review 而不是 TL 兼 review：PM 写 spec 但不写代码也不做微分解，审 dev 的交付
没有自审偏差；TL 天天和 dev 交互，由它判终局最容易「自己派自己判」。

「不替对方改代码」是硬边界——TL 改了代码，review 就分不清哪些是 dev 做的，评审链失效。

## 为什么不用 kander

`~/.agents/kander` 有 1574 行协议（12 文件 / 7 模块全开），在 `~/.config/opencode/AGENTS.md`
里被强制每个 session 加载。而全机所有项目（`php-server` / `h5` / `admin` / `apartment` /
`deepseek-harness`）**没有一个建过 kander 板**。

真正在 apartment 三个 pane 之间跑通的是：8 个文件 + 1 个巡检脚本 + 0 个命令契约。
本项目把那套协议升一级（补上 PM、给工件加轮次、盯全部三个 pane 而不是只盯一个），
没有继承 kander 的任何机制。

从 apartment 实测继承的教训构成本项目的设计依据：

| 教训 | 这里的对应 |
|---|---|
| 门铃返回码 ≠ 送达（实测 2 次 ALERT-FAILED） | `say` 自动补 `send-keys enter`，判据是状态转换 |
| 文件 mtime 不是存活信号 | 巡检用 `agent_status` + `state_change_seq` |
| 用 mtime 猜「消费了没有」，误报 6 次 | 判据是 `verdict.round != consumed.round` |
| 编排者越界自己改代码，责任不清 | 三个角色各自有「不做」清单 |
| 静默退出 = 没有机制 | 巡检异常在 `events.log` 留大声原因，进程脱离进程组防连坐 |
| 用局部证据下全称否定，4 次连续误判 | verdict 的 finding 必须带行号 + 可复现证据 |

### 章程变更是可检测的，不是靠人记得

`up` 时章程一次性投进 pane，之后你改了 `roles/pm.md`，正在跑的 pane 拿到的还是旧的；
而 `PROTOCOL.md` 是「源比副本新就自动覆盖」的。两者规则不一致，于是「我改了章程怎么
没生效」要靠人自己想起来跑 `sync`。

所以 `.xteam/rules.json` 记下**投进 pane 的是哪一版**（每份章程 + 协议的 sha256）：

- `status` 主动提示「规则改了但正在跑的 pane 还是旧的：pm —— 跑 xteam sync」
- `sync` **只重投真的变了的那几份**，并且重投后更新指纹
- 没记录时不报警（首次 `up` 之前报「过期」是噪声）

用指纹而不是 mtime：mtime 会因为 checkout、rsync、编辑器改写时间而漂，指纹只认内容。

### recap：按需、限长、覆盖写

recap 是给「接手的人扫一眼」的，不是上下文主体。三条约束都是为了 token：

- **只在真正参与过那个切片时写** —— 判据是工件本身（谁写的 `delivered.json`
  谁就是 dev），没参与的人不凭空编一段
- **15 行以内、覆盖写** —— 追加会让文件无界增长，而注入时只看得到尾部
- **注入别人 recap 时每份限 600 字** —— 两个角色合计从 2400 字降到 1200

记账用独立的 `recap_asked` 字段，**不碰 `alerted`** —— 后者是 0/1/2 的告警阶梯，
塞字符串进去会让 `alerted < 1` 抛 TypeError，而那行在 working 分支里，
agent 一转 working 巡检就崩。

### 身份进系统提示词，现状留给文件

长跑必然撞上上下文被重置（`/new`、`/clear`、压缩）。原设计把章程**投在对话里**，
于是重置一次，agent 就退回「你好，请问要做什么」—— 整条协作链要重新解释一遍。

拆成两半：

- **身份**（你是谁、章程、重置后先干什么）进**系统提示词**
  （`.xteam/identity/<角色>.md`，omp 走 `--append-system-prompt`）。
  实测 omp 18.4.9：`/new` 换会话（herdr 的 `agent_session` 路径随之变化）、
  `/clear` 只丢消息（会话继续），**两者都动不了进程的系统提示词**。
- **现状**（欠什么、做到哪）本来就该在文件里（「状态是文件」那条），
  `xteam whoami` 把它渲染成一屏，供任何新会话接上现场。

重开于是变成日常操作而不是事故：`xteam reopen <角色>`（原地换会话，
pane/进程不动）或 `xteam swap <角色>`（换进程，kind/model 都能换）。

两条边界：

- **没有这个 flag 的 kind 不装作有**。表里只有实测过的（`SYSTEM_PROMPT_ARG`）；
  其余 kind 退回「章程投进对话 + 每条门铃自带身份提醒」——对它们来说，
  重置就是全部忘光，提醒必须先于内容到达。
- **巡检只提醒、不自动重开**：重开丢掉的是对话里还没落文件的推理，
  值不值得丢由人判断；但提醒不能省 —— 上下文一满，agent 就开始
  「压缩之后凭印象干活」，那种坏是安静的。
