## 第三方评审（冷读视角）

pm 和 tl 用的是不同 agent/model，但**读的是同一份 spec.md**——如果错在 spec 本身
（漏了边界条件、验收判据不可判定），两个角色会一起错。

所以有一个**没参与过这个项目**的外部 agent 冷读 spec 和 diff：

```bash
xteam qa show                     # 看配置
xteam qa set --agent qodercli --when risky    # 固化配置
xteam qa run                      # 跑一次（结论落盘 + 门铃 pm）
xteam qa clear                    # 回到默认
```

它问两件事：**需求本身有没有遗漏/歧义/不可判定的判据**，以及**改动是否真的满足验收**。

| `when` | 行为 |
|---|---|
| `manual`（默认） | 不自动跑。多数切片 pm 和 tl 已经审够了，每轮都跑会拖慢门禁 |
| `always` | 每次门禁前自动跑 |
| `risky` | 共享契约项目（`shared-api`）+ `--project` 指定的，自动跑 |

**它不是裁判。** `verdict.json` 仍然只有 pm 一个作者。外部工具挂了也不会让门禁停摆
——巡检会把「没跑成」一起带给 pm，然后照常判。

### 为什么不加成第四个常驻角色

三个 reviewer 意味着意见可能冲突（tl 说 PASS、qa 说 FAIL），而裁决权只会更集中到 pm。
更要命的是：常驻角色必然读过同一份 spec，**它会犯和 pm/tl 一样的错**。
外部进程的价值恰恰在于它**没有**那些上下文。

实测：`qodercli -p -w <dir> "<prompt>"` 约 24s 返回，能读到仓库里的文件。
结果落在 `.xteam/tasks/<切片>/external-review.md`。
