# 多项目与 API 契约

← 返回 [README](../README.md)

## 从单项目迁到多项目

先在单项目上用起来，等仓库真的长出第二个项目再迁——**不用一开始就声明成多项目**：

```bash
xteam init                     # 单项目：xteam init --repo-kind single
xteam up . --watch
# ... 项目长出 frontend / api / admin 了：
xteam init --force --repo-kind multi-api --projects frontend,api,admin --shared-api api
```

`--force` 只覆盖 `.xteam/projects.json` 这份声明，**不动** `tasks/` `wiki/` `memory/`
`contracts/` 里的任何东西。已存在的切片如果没写 `project`，迁完会立刻被
`name-project` 门禁拦下——补上 `task.json` 即可，这正是「先单后多」唯一的代价。

## 跨项目切片排序（depends_on）

跨项目的需求**按项目切成多个切片**再排序，而不是一个切片跨两个仓改代码
（那样 review 时无从判断越界）：

```json
// .xteam/tasks/api-side/task.json
{"project": "api", "contracts": ["POST _orders.md"]}

// .xteam/tasks/frontend-side/task.json
{"project": "frontend", "depends_on": ["api-side"]}
```

前置没闭合时，后继切片归 `tl: wait-dep`——**这不是卡住，是还没轮到它**。
`xteam status` 会单独列出「等前置」，避免看起来像卡死。

三类情况刻意分开，因为混在一起会把「写错了」当成「还没做完」：

| 情况 | `xteam status` 显示 |
|---|---|
| 前置存在但未闭合 | `等前置（不是卡住）：frontend-side←api-side` |
| `depends_on` 拼错了名字 | `⚠ 指向不存在的切片（拼错了，不是排队）` |
| 依赖成环 | `⚠ 依赖成环：a → b → a` |

`xteam contracts check` 一次查全这三类，加上契约文件名是否合规。

## API 契约（跨项目专用）

跨项目最常见的失败不是代码写错，而是**前端照着记忆里的接口实现**。
所以动共享契约层时，改了什么必须留下可查的约定。

**约定：一个契约一个文件**，文件名是 `METHOD /path`，路径里的 `/` 写成 `_`
（文件名不能直接带斜杠）：`POST /orders/{id}` → `POST _orders_{id}.md`。

```bash
xteam contracts new "POST /orders"   # 建骨架（请求/响应/错误码/变更记录）
xteam contracts list                 # 列出契约，以及哪些切片引用了它们
xteam contracts check                # 查依赖环、拼错的前置名、不存在的契约
xteam contracts log "POST _orders.md" "total 改为字符串"   # 改完留痕
```

切片在 `task.json` 的 `contracts` 里声明它改了什么。**声明了却没有对应文件时，
PM 会被 `contracts-missing` 拦下**——先定契约再改代码。

改完契约要留痕：

```bash
# 往契约的「变更记录」追一行，同时落到共享时间线，并提示哪些下游受影响
xteam contracts log "POST _orders.md" "total 由数字改为字符串"
```

`log` 还会顺手提醒「下游会受影响：fe、admin」——改契约不留痕，下游就无从判断
自己手里那份实现还能不能用。

`contracts/` **只在存在 shared-api 项目时才建**——单应用仓库没有「下游」这回事，
建个空目录只是噪音。同理，契约门禁也不拦普通项目。
